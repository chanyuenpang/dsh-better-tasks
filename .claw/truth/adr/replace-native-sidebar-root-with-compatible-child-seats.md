# ADR: Replace the native sidebar root with compatible local forks and Host-owned task state

## Context

The project must own the sidebar shell and provide a durable pinned-task workflow while preserving the native Workspace Browser, Settings, branding, global panels, footer actions, expanded layout, collapsed rail, Session lifecycle, and conversation interactions.

Cordis slot children belong to the root registration entry that declares them. A replacement root cannot safely render the shipped root's children merely by winning single-slot priority. The shipped workspace, layout, and question packages also expose no stable public extension points for the required Session-tree filter, row Pin action, shared create hook, expanded width contract, or task-card question surface.

Pin membership and manual order must survive refresh, restart, and another browser. Pin and Unpin must also acknowledge a click without waiting for a Host round trip, without weakening revision-CAS or letting speculative membership become persistence input. Goal, Todo, Session, Workspace, sidebar width, pending questions, and project appearance already have owners whose business semantics must not be duplicated.

Presentation preferences must persist across browsers and process restarts, update immediately, and remain independent per projection without introducing a second browser-local source of truth. Settings support is optional infrastructure, so its absence cannot hold the sidebar or core Web surfaces in a service wait. Production must load a reproducible immutable package rather than the development checkout, and a scoped browser package must use the same ModuleLoader identity as its npm name. Any shell-wide composition change must cold-start safely before it is installed into the real Web profile.

Desktop 0.2 removed the legacy current-Session catalog field while retaining the existing selected-card styling. A background Agent can be running without owning the main view, and a non-conversation panel can cover a retained Session. Selection therefore requires the native view contract, not inference from Agent activity or a new persistent card flag.

Desktop 0.2 input adds another ownership boundary: native trigger/command UI is Session-singleton state, while task cards must work independently of the open main composer. A bare binding lookup or a short lease around void-returning submit cannot own asynchronous readiness and settlement. The user required in-card native skill/command interaction, then rejected the first adapted presentation despite accepting its functionality; native parity must therefore preserve the established compact UI and microinteractions.

The Desktop settings review distinguished correct Host persistence from stale client disclosure overrides and unsafe renderer storage initialization. Repairing those boundaries must preserve same-cycle manual choices, avoid resets on Todo progress, tolerate storage denial and keep the established idle/Final input gate without inventing a native round identifier. A later restart incident established that native cold catalog metadata can temporarily expose an older creation timestamp before hydration restores activity; inequality alone is not evidence of a new cycle. Card-level Final expansion must also preserve immediate single-click opening and must not compete with Final-body or nested-control gestures.

Desktop zero-width collapse exposed another root-replacement obligation: disabling native sidebar also removes its outside-column caption controls and macOS shell seat. A column-only reopen button can be clipped even while the subtree remains mounted. Restoring access must not transfer width/collapse ownership or undo accepted task behavior.

## Decision

Deliver the feature as the regular project-local `dsh-better-tasks` Host/Client Cordis package.

At composition time, disable the shipped `ui-sidebar` root and register `BetterSidebarRoot` as the sole `sidebar` root. The replacement entry declares the same six root-scoped child seats for brand mark, brand name, panel list, Workspace Browser, Settings, and footer action, and renders existing registrants through those seats.

Use exact, project-local compatibility forks of `@deepseek-ai/dsh-client-ui-workspace`, `@deepseek-ai/dsh-client-ui-layout`, and `@deepseek-ai/dsh-client-ui-user-questions`, matched to the target runtime. The `0.1.5-rc.2` baseline belongs to the legacy Web line; the Desktop repair targets `0.2.0-rc.2`. Keep fork provenance and patches replayable. Do not modify the DSH installation or shipped preset. The initial Desktop workspace repair was limited to Better Tasks/workspace, retaining installed layout/questions. The later accepted input adaptation adds runtime-matched input-trigger, commands and conversation forks while reusing the three accepted layout/workspace/questions artifacts; this is a separately verified composition, not permission to deploy unrelated diagnostic work.

Restore the native Desktop outside-column affordances as part of sidebar replacement: reuse Windows caption positioning for the existing controls and register reopen/New Session in the legal root-scoped `shell.leading` seat. Delegate to native public actions; let the frame own macOS visibility/position and the layout fork own collapse and last positive width. Do not create a second root, layout store, DOM-injected control or new hard service dependency. Preserve browser rail behavior and existing task/child-seat contracts. [Canonical Truth](<../sidebar-replacement-and-task-swimlane.md#desktop-zero-width-sidebar-reopen>) owns current implementation anchors and version-bound release evidence.

For abnormal task execution, extend the existing whole-card state language with a red state rather than adding a banner or a second task-state owner. Derive warning state from durable turn-event projection plus the optional native connection state; a lost connection is explicitly unknown, not evidence that background execution stopped. Preserve normal completion and pending-interaction semantics and existing continuation behavior; do not retry automatically.

Assign ownership as follows:

- Better Tasks Host owns one versioned `better_tasks_pin_queue` record and exposes revision-CAS pin, creation-pin, unpin, and reorder mutations. The ordered Session-id list is the sole task-membership and order truth.
- Better Tasks Client may project reversible per-Session Pin or Unpin intent over its last confirmed Host queue and publish it before the serialized request tail. Host commands and `expectedRevision` are always derived from confirmed state; a valid conflict snapshot is adopted and retried once, and terminal failure discards the intent so the projection rolls back.
- The workspace fork owns native Session-tree presentation additions: activity filtering, row Pin state, one `onSessionCreated` lifecycle seam covering every create-or-reuse entry, and one visual-only `aria-hidden` `📌` before a pinned title. The marker renders from the same confirmed-or-optimistic pin projection; the existing Pin/Unpin button remains the interactive and accessible state source.
- The layout fork remains the only sidebar-width owner and persists a 264px minimum, 280px default, and `max(840px, 50vw)` ceiling.
- Session, Workspace, Goal, Todo, and pending-interaction semantics remain with their native owners. Better Tasks reads their projections and delegates card actions to native mutations rather than duplicating those domains. Todo, Goal, Final, and the idle quick-message input use separate presentation keys and explicit boolean defaults. Manual overrides win within their own lifecycle. Bind Todo to Goal ID and ordered list contents, not completion progress; unknown projections must not clear choices. Bind Final and input to the existing shared idle cycle, preserving drafts and other projection choices. Use functional updates so concurrent projection effects do not overwrite one another. [Canonical Truth](<../sidebar-replacement-and-task-swimlane.md#settings-and-expansion-review-boundary>) owns implementation and migration details, including the monotonic native activity watermark, cold-hydration protection and current-task suppression. Use the native `task.current` projection rather than a second focus owner; consume suppressed cycles so navigation cannot replay automatic expansion. Preserve explicit manual expansion and resolve effective disclosure synchronously before effects. Goal and the quick-message input default to collapsed, and Todo state never mutates Goal state. Input visibility is nevertheless gated by Final expansion: closing Final hides the input without discarding its current draft or manual input override.
- The idle-only quick-message control depends on Final disclosure but not successful Final content retrieval. Preserve the existing `defaultInputExpanded` settings key while labeling its control “Quick message bar”; keep an unsent draft mounted when Final is collapsed. Send user text through the native Session binding in `steer` mode, substituting the localized default continuation for an empty or whitespace-only draft, then best-effort resume an existing incomplete Goal through an optional Goal remote. A Goal failure produces a visible warning without treating an admitted prompt as unsent; a prompt failure keeps the draft for retry. Rename a Session title through the native `session.rename` binding and a DSH `Modal`/`Button` dialog, selecting the existing title on open without taking over the rest of the card's open-Session action. The later unscoped `0.2.18` main archive was installed in the real profile with the three existing fork dependencies and patch unchanged; no real restart or current-page activation was confirmed.
- For Desktop, use explicit independent native surfaces rather than the legacy skill-only textarea, a shared Session singleton, private methods or a handoff to the main input. The input-trigger/commands/conversation forks retain native editors, candidates, command parameters and execution, but give each surface its own token, draft/revision, trigger and popup. The real Session is retained before readiness until admitted work settles; UI closure invalidates new operations while allowing settlement and late draft restoration. Optional provider lookup fails locally without blocking the core shell. [Canonical Truth](<../sidebar-replacement-and-task-swimlane.md#desktop-independent-task-input>) owns the implementation boundary and code anchors.
- Preserve the accepted compact task-card UI while reusing native behavior: one combined skill/command plus picker, independent search, captured-selection CAS insertion, caret/focus handoff, IME/repeat protection and isolated failure feedback. Ordinary messages use the native conversation send transaction with post-admission Goal handling; native commands never fall back to prompt delivery. Attachment intake is not part of this surface. The historical Web skill-only decision did not provide slash execution; the accepted Desktop adaptation supersedes that restriction only for its own release line.
- The user-question fork exposes the official renderer, shared draft state, and single-settlement gate as `questionSurface`. Apply compact question text and button styling only within the task-card variant rather than changing the native conversation surface. Better Tasks looks the service up optionally; missing support falls back to the native Composer rather than blocking core UI activation.
- Better Tasks adopts the existing `workspace_appearance` domain name, version, table schema, and HTTP contract so prior data remains valid without a second provider.
- Preserve immediate single-click Session navigation while making the second non-control card click toggle Final, as explicitly requested after the expansion-only shortcut. Immediate close must not depend on content retrieval; cancel pending shortcut reads and body timers, and commit manual choice against the effective lifecycle. Opening still requires bounded nonempty Final; asynchronous replies may only open, never toggle. Retain native-current suppression, monotonic activity consumption and independent same-cycle projection choices. [Canonical Truth](<../sidebar-replacement-and-task-swimlane.md>) owns code anchors and the version-bound 0.2.17 installation evidence, not a second deployment ledger here.
- Final is a bounded read projection, not a new transcript owner: the Host returns only the latest ended current-surface assistant text for a pinned Session, limited to 4000 Unicode code points; the client may cache that safe payload and idle-cycle expansion state. Keep pending click feedback exclusively in the Client Final click controller and per-Session render state, not Host API or durable settings. A non-link click marks the detail pending immediately; clear that state before the delayed single-click input toggle or double-click Final collapse. Manual collapse and teardown cancel pending work, while Markdown links retain navigation and keyboard activation stays immediate. The current checkout uses a 300ms click window; the installed `0.2.18` checkpoint and its test used 600ms, so release timing must be scoped rather than asserted as the current checkout contract.
- Keep Host settings as the sole durable preference truth under `better-tasks-ui`, with one official `settings.section` page. Bind legacy `settingsScope` or 0.2 `configForms` optionally, falling back to defaults without blocking core activation. On 0.2 expose volatile fields from `Config` and use `entry.options.id`, not Inspect's qualified loader identifier. Treat `set()` resolving `false` as rejection and wait for a valid writable snapshot before migrating the legacy view preference; remove legacy data only after an accepted write. Reversible optimistic feedback must resynchronize on failure. Do not maintain a second localStorage settings owner. Keep lightweight per-client disclosure records in guarded renderer storage, falling back to React memory if access/getters/reads/writes fail; do not add file/IPC persistence or a hard dependency. A storage failure must not retire the sidebar or overwrite Host defaults.
- Explicitly request 0.2 pinned-session projections from the existing Sessions service rather than treating catalog membership as proof that Todo/Goal values have loaded. Keep pin callbacks Promise-preserving and workspace hook bindings explicit; failures must not silently retire the workspace slot.
- Publish the main package publicly as `@veewo/dsh-better-tasks`, but treat the real Web profile's unscoped `dsh-better-tasks` as a separate, independently versioned local release line. An npm publish is not a Web deployment: record whether the local package remains unchanged, is installed but awaiting an authorized restart, or has actually activated. Stage the local package with `scripts/build-unscoped-release.mjs`, pack it into a new immutable archive, and use the exact candidate-composition sandbox gate before real-profile installation; `docs/release.md` owns the detailed release procedure. The browser ModuleLoader id must match its package identity; never live-switch a running Client plugin from unscoped to scoped. Perform any identity migration only while the Host is fully stopped; a fork-only release may retain the stable main-package identity and update just the immutable fork artifact. Keep the three exact forks as version-locked release assets until they have independently publishable identities.

Require the exact candidate composition to cold-start in an isolated sandbox with separate `DSH_HOME`, profile, Session storage, and ledger and with Cindy Host disabled. Host listening, browser-shell activation, core Session/Workspace/conversation surfaces, and zero startup errors take precedence over optional feature completeness. Only after that gate passes may the real composition be changed or `dsh web` restarted. Treat automated, sandbox, and browser checks as technical release evidence; final product acceptance belongs to the user and requires the user's explicit confirmation.

For Desktop acceptance, use the installed Electron application's `dsh-app://app/` shell with its preload/IPC environment and independent user-data as well as isolated Host storage. An HTTP browser is auxiliary evidence, not a substitute. Stop all sandbox resources before real installation; any real restart remains explicitly authorized or performed by the user.

A native-named fork rejected as `not-bundle` is a partial-install recovery problem until files, manifest, wanted lock and installed lock are compared. Prefer supported installation; if files already match the verified candidate but only metadata rolled back, perform only an explicitly authorized minimal metadata alignment. Preserve existing fork rows, unrelated dependency resolutions, and concurrent user settings. Do not repeat the failed bundle operation or broadly rewrite the profile to force success.

Keep selected-card state a native Session/view projection, with no additional durable owner. Follow the generation-aware retention/panel boundary in [canonical Truth](<../sidebar-replacement-and-task-swimlane.md#desktop-02-compatibility-boundary>); legacy fallback is permitted only when the newer retention contract is absent. Repair the state mapping rather than redesigning intact CSS or introducing a service dependency. For a main-package-only fix, reuse the already-verified immutable fork archives instead of rebuilding unrelated forks, while still cold-starting the exact resulting composition. Referenced release directories remain dependencies, not disposable older builds. Installation and user-performed restart acceptance remain distinct outcomes.

## Alternatives

- **Force Desktop collapse to retain a fake rail, copy layout state, or restore the old overall layout:** rejected because native zero-width/frame ownership is intentional and the repair must preserve accepted width and task behavior. Restore the omitted chrome affordances through native actions and the legal shell seat instead.

- **Priority-shadow the shipped sidebar root:** rejected because a winning root is not authorized to render child slots declared by another entry.
- **Keep both sidebar roots and redeclare child seats:** rejected because duplicate declarations fail activation.
- **Use only a task-settings picker and leave the Workspace Browser untouched:** rejected because the selected product behavior requires actual Session-tree filtering and one row-level Pin entry.
- **Inject Pin/filter controls into native DOM:** rejected because Session identity, React reconciliation, drag behavior, keyboard behavior, styles, and lifecycle are not stable DOM contracts.
- **Copy Workspace Browser, layout, or question business logic into Better Tasks:** rejected because it creates competing owners and excessive parity risk. Exact, narrow forks retain the upstream owners and make differences auditable.
- **Persist task membership or order in browser storage:** rejected because it cannot provide global cross-browser truth or safe concurrent mutation.
- **Wait for each Host Pin mutation before updating membership:** rejected because round-trip and serialized-tail latency make the primary control appear unresponsive even though persistence remains correct.
- **Use optimistic membership or revision as the next CAS baseline:** rejected because speculative state is not authoritative and can corrupt conflict handling; optimistic intent is projection-only.
- **Hard-inject `questionSurface` or settings support:** rejected because an unfinished optional provider can hold the root layout and all dependent UI in a Cordis service-wait chain.
- **Persist presentation settings in localStorage:** rejected because Host settings already provide the cross-browser durable truth; a second store would create divergence and ambiguous rollback.
- **Move disclosure persistence into a new file/IPC owner or hard-inject storage:** rejected because lightweight presentation can safely degrade to memory while Host ConfigForms already owns defaults; extra ownership and startup coupling are unnecessary.
- **Reset Todo on progress or clear every choice on upgrade:** rejected because same-cycle manual intent must survive progress and refresh. Use Goal/content identity and bind unowned legacy overrides only when projections are determinate; do not erase saved disclosure to repair the cycle classifier.
- **Treat every unequal Final activity observation as a new cycle:** rejected because cold metadata fallback can lower the marker and hydration can reset the same cycle again. Accept only valid, strictly increasing activity; equal, older and unknown observations retain choices and consumed watermarks without adding a native round ID or metadata writer.
- **Delay card single-click opening to detect double click, read Final before closing, or toggle on asynchronous completion:** rejected because navigation remains immediate, closing must work even without available content, and late responses must not reverse a newer manual choice. The accepted user-requested shortcut toggles synchronously: close immediately with cancellation, or confirm bounded nonempty Final before opening. Reuse the existing projection rather than creating another content owner.
- **Persist a second current-task flag or postpone suppression until effects:** rejected because native view projection already owns current identity, while delayed suppression can flash open or trigger lazy reads before it applies. Consume the suppressed cycle and share effective disclosure across rendering and gestures.
- **Store Final as a second durable transcript:** rejected because Session history is already canonical; Final is a bounded on-demand projection.
- **Persist pending click feedback or act on the first click immediately:** rejected because the feedback is a temporary visual distinction while single versus double click is unresolved; performing input toggle before double-click determination would leave a second action to undo.
- **Require successful Final content retrieval before showing quick-message input:** rejected because a failed or empty read projection must not block a native Session action once Final is expanded.
- **Keep quick-message input visible while Final is collapsed:** rejected because the input belongs to the Final disclosure area; hiding it must retain its draft and manual disclosure choice.
- **Resume Goal before sending, or fail the send when Goal resume fails:** rejected because the user's prompt may already be admitted and must not be reported as unsent; a best-effort post-send warning preserves the distinction.
- **Submit slash-looking text through the quick-message prompt and call it a command:** rejected because the prompt binding does not provide native candidates, parameter collection, or command execution, and a card must not accidentally target the currently open Session instead of its own Session. Reusing a single native editor DOM root across multiple cards is not an equivalent per-card composer contract. A catalog-selected user skill `/name ` text gesture has a separate native Host validation path and does not change that command limitation.
- **Copy command business logic, hardcode catalogs, share the main editor/singleton, or redirect users to the main composer:** rejected because these approaches lose native semantics, surface isolation or the requested in-card interaction. Reuse native behavior through explicit per-surface contracts instead; a Host-only command subset is not full native adaptation.
- **Replace the accepted card design merely because native internals changed:** rejected after the functional `0.2.9` adaptation failed presentation acceptance. Preserve existing UI/UX and test focused interaction contracts without adding unsolicited visual-measurement QA.
- **Retain only around the submit call, or release immediately on UI disposal:** rejected because readiness, popup callbacks and asynchronous submission can outlive both the call and the visible card. Session ownership extends through settlement.
- **Revert unrelated concurrent plugin updates or reuse acceptance from an old dependency graph:** rejected because the installed graph, not an earlier snapshot, is the candidate composition that needs validation.
- **Copy native rename UI internals or maintain a card-local Session title:** rejected because the public native `session.rename` binding owns persistence and projection updates, while reusable DSH dialog primitives provide the desired interaction.
- **Load production from the development checkout or replace a same-version tarball:** rejected because the deployed code would not be reproducible and pnpm may retain a cached package. Release fixes require a new semver, a rebuilt immutable artifact, and a clean package installation.
- **Live-switch the running Client from an unscoped to a scoped package identity:** rejected because the old and new locale fibers can overlap and register the same locale namespace twice. Package-identity migration requires a fully stopped Host.
- **Patch the DSH installation or shipped preset:** rejected because upgrades overwrite those changes and rollback becomes unsafe.
- **Accept Desktop from Host listening or an HTTP browser alone:** rejected because those checks do not exercise Electron preload/IPC and the actual renderer activation path.
- **Use Inspect's qualified loader path as the settings namespace, or interpret a resolved `false` as success:** rejected by the Desktop settings contract; either can lose persistence or incorrectly discard legacy data.
- **Assume failed bundle installation restored package files, or deploy all staged forks during a narrow repair:** rejected because metadata rollback and filesystem state can diverge, while unrelated candidates have not passed the same exact-composition acceptance.

- **Use Agent `running`, retain an unconditional `list.current` fallback, or persist a card-selected flag:** rejected because background execution is not main-view selection, stale legacy ids must not override the newer contract, and the native Session/view already owns this state.
- **Rewrite selected-card CSS or rebuild all forks for a mapping-only repair:** rejected because the styling was intact and unrelated artifact churn would enlarge the candidate beyond the repair. Reused forks still participate in the exact-composition startup gate.

## Consequences

Root replacement must preserve native chrome outside the sidebar column as well as child-seat compatibility. Desktop platform-specific caption styling needs narrow contract coverage, while shell-seat visibility remains frame-owned. A main-only repair can reuse the accepted layout and other immutable forks, but still requires the exact-composition startup gate and cleanup before installation. Unit/static CSS and startup evidence are not collapsed-state functional or visual acceptance; real restart and product acceptance remain user-owned. Detailed 0.2.18 results belong to canonical Truth, not a second deployment ledger here.

The project can provide a native-feeling pinned-task sidebar while preserving existing child registrants and business owners. Host revision-CAS makes stale writes explicit and manual ordering durable, while reversible Client intent makes Pin and Unpin visible before Host completion. This introduces a deliberate two-layer Client model: concurrent intent may affect presentation, but serialization, conflict retry, revision, update time, and durable membership remain anchored to confirmed Host state. The shared create hook gives all creation paths one idempotent auto-pin rule without rolling back a successfully created Session when pinning fails.

The design deliberately accepts maintenance cost: the three base forks and, for the Desktop input composition, three additional native input forks must remain replayable and runtime-matched. Rebuild and check changed forks against upstream, reusing unchanged accepted artifacts in the exact-composition startup gate. Composition is stricter because shipped and local owners for the same root/package cannot be active together. The local package now owns durable pin and appearance domains, so rollback must preserve their data even when UI rows are restored.

Host-backed preferences provide one cross-browser source of truth while separate projection keys prevent one control from rewriting another; input remains Final-gated. The accepted Desktop repair bounds manual overrides by projection lifecycle without moving settings ownership or clearing drafts. Per-client memory fallback deliberately sacrifices disclosure persistence when renderer storage is unavailable, rather than failing core UI. Todo cannot distinguish identical content reissued under the same Goal without a new native version identity; Final still reads native `updatedAt`, but its consumed watermark never moves backward: the confirmed cold-catalog fallback/hydration reset is repaired without inventing native cycle identity. Strictly newer activity remains the reset signal; absent renderer storage still cannot promise restart persistence, and previously erased manual records cannot be reconstructed. Card double-click is an explicit disclosure toggle, not a second transcript owner or a delayed navigation mechanism. Closing cancels pending reads and body timers without retrieving content; asynchronous retrieval may only open after confirmation. Manual disclosure consumes the effective lifecycle marker with its explicit choice so a background cycle not yet persisted cannot erase manual close, without changing same-cycle input/draft or Goal/Todo ownership. [Canonical Truth](<../sidebar-replacement-and-task-swimlane.md#settings-and-expansion-review-boundary>) owns the detailed implementation, migration and version-bound repair evidence; installation is not user acceptance. Optimistic settings feedback requires rollback to the latest Host snapshot after failure. Immutable package deployment adds release discipline: each changed release line needs a new version, fresh build and exact-composition sandbox package gate; npm publication and clean local-profile installation are separate outcomes, not interchangeable steps. The development checkout cannot serve as the production source.

Optional integrations must remain optional until their providers pass the same candidate-composition startup gate. A missing question surface degrades only task-card answering, missing settings support degrades only persistence and editing, and missing Goal remote degrades only post-send Goal recovery with a warning; none may block the sidebar, Session, Workspace, or conversation surfaces. The earlier unscoped `0.2.9` main candidate passed 76 tests and its isolated exact-composition startup/core-browser gate with the existing three forks. The later `0.2.18` main candidate passed 78/78 tests and an isolated exact-composition Cindy-disabled cold start with core browser shell free of errors; sandbox listeners were cleaned up before only the main package was installed. The patch and fork dependency paths stayed unchanged, and the original Web process (PID 40784 on port 3080 at that checkpoint) remained running without restart; installation does not establish current-page activation or user visual acceptance.

The later unscoped `0.2.23` focus-and-drag main candidate passed 83/83 tests and the isolated exact-composition cold-start/core-browser gate with Cindy Host disabled; sandbox cleanup preceded main-only real installation. The original process remained listening without restart, so neither live activation nor per-card slash support follows from that checkpoint. The subsequent `0.2.24` skill-only picker passed 86/86 tests and an isolated Cindy-disabled exact-composition startup/core-browser gate; its sandbox was cleaned before main-only installation with forks and patch unchanged. The real 3080 process still was not restarted or hot-reloaded, so installation does not prove live picker activation, browser-card acceptance, or per-card native command integration. At that legacy Web checkpoint, native integration remained a separate task; the subsequent accepted Desktop surface adaptation is recorded in canonical Truth and does not retroactively change the Web checkpoint.

Every real-profile change requires the sandbox-first gate and a composition rollback plan. The sandbox must never share live ledger or storage state. If live startup fails, restore the last known-startable composition before attempting feature repair. Technical checks can authorize release progression but cannot substitute for explicit user acceptance.

A package-identity change now has a stricter operational cost than an ordinary version update: the Host must be fully stopped before composition identity changes, while a fork-only release should prefer the stable main-package identity when that satisfies the change.

Desktop compatibility adds a generation-specific settings adapter and a real Electron startup gate, not another preference or task-state owner. Package-manager error handling must account for partial filesystem mutation, so recovery verification covers artifact identity, both locks, composition, and preservation of unrelated state. Version-bound repair and acceptance facts are owned by [canonical Truth](<../sidebar-replacement-and-task-swimlane.md>); earlier Web installation-without-activation checkpoints above remain historical and do not negate the later user-confirmed Desktop restoration.

Selection compatibility remains generation-aware without adding persistence or coupling optional services to core startup. Regression coverage must distinguish the selected Session from running background work and suppress selection for non-conversation panels and absent main-view retention. Main-only deployment reduces unrelated changes but obliges retention of every referenced immutable fork archive. Detailed implementation and the accepted Desktop `0.2.8` checkpoint remain in [canonical Truth](<../sidebar-replacement-and-task-swimlane.md>), rather than a second deployment ledger here.

Surface isolation adds explicit asynchronous ownership and close/settlement bookkeeping, but avoids copying native command semantics or coupling card drafts to the main composer. Recheck the profile dependency graph immediately before installation, preserve concurrent updates and validate the resulting composition if it has changed. Product acceptance remains separate from installation-time restart requirements; [canonical Truth](<../sidebar-replacement-and-task-swimlane.md#accepted-independent-desktop-input-while-restoring-the-original-uiux>) records the user-confirmed Desktop outcome without creating another deployment ledger here.

## Decision evolution

<!-- dated: 2026-09-30 -->
### Replaced the Desktop skill-only boundary with isolated native surfaces

The legacy narrow prompt/skill picker was not a native command surface. Desktop adaptation instead added explicit per-surface contracts and real Session lifetime ownership, keeping native execution in-card without borrowing singleton state. Functional acceptance of `0.2.9` did not authorize replacing established UI/UX: `0.2.10` restored the compact presentation and combined plus interaction. Concurrent dependency drift also established the need for an immediate preinstall graph check and preservation of unrelated updates, not rollback to an obsolete sandbox snapshot.

<!-- dated: 2026-09-30 -->
### Replaced legacy selection authority with native view ownership

The Desktop selection incident showed that intact selected-card styling cannot compensate for a removed catalog field. The accepted repair kept the visual design and native ownership, replaced the legacy-only mapping with generation-aware view projection, and confined deployment to the main package with already-verified forks. This preserves legacy compatibility without allowing stale legacy selection or background execution to masquerade as the current view.

<!-- dated: 2026-09-30 -->
### Required Desktop-native acceptance and narrow partial-install recovery

The Desktop repair exposed two misleading success assumptions: a listening Host/ordinary browser did not establish Electron renderer compatibility, and a failed native-named fork installation did not restore already-replaced package files. The accepted approach required isolated installed-Electron acceptance, scoped deployment to Better Tasks/workspace, and an explicitly authorized dependency/lock-only correction after comparing installed state. The initial `include:better-tasks-ui` settings hypothesis was rejected in favor of `entry.options.id`; asynchronous readiness and false-result handling protect legacy preferences. These decisions supersede those assumptions without changing native ownership or authorizing unrelated migration work.

<!-- dated: 2026-09-23 -->
### Expanded from a read-only recent view to a durable pinned workflow

The first accepted sidebar release kept the Host free of business state and derived up to ten recent Sessions in the browser. Product decisions later required row-level Pin, persistent manual ordering, wider layout behavior, card-level pending questions, durable Final presentation, and auto-pin across every creation path. The accepted design expanded to narrow exact forks and a Host-owned CAS queue rather than introducing DOM injection, local-only state, or copied native business logic.

<!-- dated: 2026-09-24 -->
### Separated fork rollout from main-package identity migration

The initial pinned-title rollout attempted to replace the running unscoped main Client package with the scoped public package while also updating the Workspace fork. Duplicate locale registration demonstrated that a live package-identity switch is not equivalent to an ordinary immutable version update. The accepted rollout kept the stable unscoped main-package composition and changed only the Workspace fork after a clean restart; future identity migration is a separate fully stopped-Host operation.

<!-- dated: 2026-10-01 -->
### Kept Final-gated input while replacing inequality-based cycle resets

An earlier source-only design allowed the follow-up input to remain visible even when Final was collapsed. The later accepted behavior gates input visibility on Final expansion while retaining its separate persisted default, manual override, and unsent draft. This distinction matters when revisiting presentation independence: separate state does not imply independently visible UI.

The later Desktop restart incident superseded inequality-based Final-cycle consumption: a cold metadata fallback is an older observation, not new activity. The accepted monotonic watermark and native-current suppression preserve the same ownership and Final/input gate rather than moving storage to Host/IPC, clearing all records or introducing a second focus store. Immediate single-click navigation also remains unchanged; card double-click expansion reuses the bounded Final projection and is distinct from Final-body collapse. [Canonical Truth](<../sidebar-replacement-and-task-swimlane.md#bounded-disclosure-overrides-then-monotonic-desktop-final-activity>) owns the version-bound repair and installation checkpoint; this decision does not claim user restart or acceptance.

The subsequent explicit user request superseded expansion-only card semantics with open/close toggling. The former rejection of card-level collapse no longer applies; the rejection of delayed navigation remains.
