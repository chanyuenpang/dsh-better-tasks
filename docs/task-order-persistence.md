# 完整任务顺序持久化（Tasks 0.4.6）

任务成员仍由官方 Workspace Pin 唯一拥有。Better Tasks 的 native-order v1 记录只维护完整顺序 sessionIds、已提交 revision 和一次性旧队列导入 journal，不拥有第二份成员集合。

- 新 Pin 的成员插入完整顺序顶部并直接触发保存，不必先打开任务视图。同一快照批量新增保留快照顺序，连续新增事件后者在前。
- 手动拖动保存完整顺序；取消 Pin/归档保存删除后的顺序。隐藏空白、子代理、冷目录项仍占持久位置，客户端过滤不能删除它们。
- 启动按已保存 sessionIds 原序恢复，补入当前官方新增成员，剔除已移除成员。原生 Pin 数组的纯重排、消息、标题、工作时间及目录加载不会重排已有成员；已 Pin 空白转为非空也不二次提顶。
- 排序不读取 listSessions/listEvents 或会话历史，不再计算首工作时间。旧 manualSessionIds/manualOrderAt/时间映射保持 schema 可读，但不再参与排序，新提交不再写这些字段。无法恢复旧版从未持久化的临时显示顺序。
- 启动存储打开期间与写入期间保留有序成员变化，尤其取消 Pin 再重新 Pin 同一 ID 必须作为重新插入，不只采用最后一个成员集合。

## 0.4.6：明确新建任务直接置首并持久化

原生 `onSessionCreated` 的明确创建成功结果（含复用已 Pin 空白会话）直接前插该任务，不读取 Session 创建日期、首次工作时间或历史。普通打开、消息/标题更新、目录恢复及 `blank` 提示变化不是创建事件，不自动提顶。

Client 只对已由官方 Pin 确认的成员应用创建中的显示顺序：在现有原生 Pin 动作和 Host CAS 顺序写入完成前，新项保持队首，迟到的 GET 不覆盖这次前插。复用已 Pin 空白只调整任务顺序，不重排官方 Pin 数组；新 Pin 已由 Host 排在首位时不重复写。快速创建按创建意图串行提交，后建任务始终显示在前；同 ID 的进行中创建通知合并。失败显式告警，不回滚原生 Pin，不伪造已持久化，也不重试原生创建/Pin 副作用。

成功的 Host 排序提交会保存完整顺序。刷新或重建 Host/Client 后恢复该顺序；标题、消息和运行状态变化不能重新排列。除用户手动调整、新任务前插或移除外，已有任务相对顺序不变。保存失败必须告警，不算已持久化。首次恢复没有明确创建事件时仍沿用现有恢复行为，不声称解决所有冷启动错序。

## 提交、失败与恢复

所有顺序写入由同一 Host 队列串行执行。成功持久化后才推进 revision；拖动通过 expectedRevision CAS 拒绝过时请求。存储失败不改变官方 Pin，不推进已提交 revision，不伪报拖动成功。成员仍即时可见或移除，未保存的完整顺序保留在内存并显式告警，拖动暂停；后续 GET、焦点刷新或成员事件可重试，成功后清除瞬时错误。客户端刷新有界，不无限轮询。

官方成员域和排序域没有公共原子事务：两者提交之间若进程崩溃，重启会从官方成员补齐缺项，但不能重建崩溃窗口内从未落盘的全部插入先后。不通过私有事务、回滚 Pin 或历史扫描猜测补救。

## 旧队列与提示

旧 better_tasks_pin_queue 保持只读。仅缺少 native-order 时尝试一次导入；保留 seed 顺序、先持久化 attempted 栅栏再调用官方 Pin、用户 touch/archive 优先、失败 partial、中断 uncertain 且不自动重试的规则。没有待导入成员时直接 done，不伪造 running。

初始化显示“正在恢复任务顺序”；只有真正旧队列 running 才显示“正在合并已有置顶任务”。这不是所有外部存储或 Pin I/O 都有固定耗时上限的承诺。

## 验证边界

单元/合同覆盖旧记录原序恢复、查询零调用、未打开任务页即保存、插入/拖动/删除后重启、并发和重入、失败告警与恢复、旧队列安全导入及提示分离。真实 profile 修改前仍须精确候选隔离冷启动，关闭 Cindy、隔离全部存储、确认核心 shell 激活并清理；启动门禁不代替用户功能验收，不自动重启真实 Desktop。
